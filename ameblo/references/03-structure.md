# 工程2：タイトル

以下の基準で設計する。

タイトル5案を作成する。

5案は単なる語尾違いにせず、
読者に提供する価値を変える。

主な基準：

- KWへの直接回答
- 最優先ニーズ
- 読者ができる判断
- 重要な比較・条件
- 有用な独自性
- 案件名の必要性

原則32〜40文字程度を目安にする。

5案から推奨タイトルを1つ選び、
推奨理由を記録する。

ユーザー承認を求めず工程3へ進む。

# 工程3：H2/H3初稿

リサーチDBから毎回ゼロベースで構成する。

KWタイプ別の固定テンプレートは使用しない。

原則として最初のH2でKWへ直接回答する。

記事前半で最優先ニーズ3つを満たす。

見出しは読者の意思決定に適した順に配置する。

SERP必須コンテンツを落とさない。

独自切り口を適切なH2/H3へ反映する。

指定案件は読者に必要な判断材料から自然につなげる。

FAQは必要な場合だけ設ける。

# 工程3.5：構成精査

必ず実行する。

以下を確認する。

- KWへ直接回答できるか
- 最優先ニーズ3つを満たすか
- SERP必須コンテンツを落としていないか
- 検索意図ギャップを補えているか
- SERP平均をまとめ直しただけになっていないか
- 独自切り口が実際に読者判断を改善するか
- 案件が自然に接続しているか
- 重複見出しがないか
- H2/H3の粒度が適切か
- 情報の順序が自然か
- 最終的に選択・行動を判断できるか

問題があれば自動修正する。

修正後を最終H2/H3構成とする。

「この記事を読んでわかること」の
具体的結論5項目も確定する。

まとめで扱う具体的結論8〜15項目も設計する。

ユーザーが構成だけを求めている場合は、
最終構成と必要な設計情報を出力して停止する。

## 構成だけの納品
タイトル5案、推奨1案と理由、最優先ニーズ3つ、SERP方針、競合と必須回答、検索意図ギャップ、採用する独自切り口を示す。
最終H2/H3、各見出しで回答する要点と主要出典、冒頭の具体的結論5項目、まとめ8〜15項目、CTA候補と人間確認事項を提示する。
競合の文字数結果と計測状況も示す。本文HTMLや本文文字数を生成したと偽らない。
